Limites Técnicos — O Que Funciona em Paralelo

Métrica Valor Implicação
Agentes simultâneos por workflow 16 (ou min(16, cores−2)) Max fan-out paralelo. Cores da máquina podem limitar a 14 em CPU de 16 cores.
Agentes totais por lifecycle 1.000 Hard cap de agentes spawnable numa sessão. Proteção contra runaway loops.
Itens por pipeline() ou parallel() 4.096 Max items numa única chamada paralela. Além disso, erro explícito.
Colecções RAG 5 Propostas, contratos, normas, composições, projetos. Query automática por agente.
Embedding dimensionalidade 384d BAAI/bge-small-en-v1.5. Mais leve que OpenAI text-embedding-3 (1536d).
KE vetorizados / total 66 / 86 (78.6%) Knowledge Extractions prontos para RAG. 20 pendentes de indexação.
⚠️ Bottleneck Crítico Você tem 20 agentes mas só pode rodar 16 em paralelo por workflow. Estratégia: fan-out em lotes de 16, ou usar pipeline (sem barrier) para serializar logicamente mas paralelizar por itens.

4 Padrões de Orquestração

Recomendado para Análise
Pipeline (sem barrier)

Quando usar: Múltiplos agentes processando itens diferentes através de múltiplas etapas sequenciais.

Exemplo: Varrer 100 projetos → A7 indexar cada um → A5 estimar custos → A4 gerar cronograma. Cada projeto flui independentemente. Item A pode estar na etapa 3 enquanto Item B está na etapa 1.

pipeline(items, stage1, stage2, stage3)

✓ Vantagem Wall-clock = cadeia mais lenta, não soma de todas as etapas. Máximo throughput.
Para Votação Paralela
Parallel (com barrier)

Quando usar: Múltiplos agentes independentes respondendo à mesma pergunta, depois síntese centralizada.

Exemplo: Um claim complexo. 3 agentes votam se é válido (adversarial verify). Síntese lê todos os votos e decide.

parallel([agent1, agent2, agent3]).then(synthesis)

✓ Vantagem Verdade por consenso. Evita single-point-of-failure em decisões críticas.
Roteamento Inteligente
Fan-out com Fallback

Padrão: Tenta A1-claims. Se falha ou confiança <70%, fallback para A3-contratual.

Implementação: Router determinístico (zero tokens) classifica entrada. Se A1 falha, dispatch para A3 automático. Sem retry desnecessário.

if agente_falha: fallback[agente_alternativo]
Para Esgotar 20 Agentes
Fan-out em Lotes de 16

Padrão: Dividir 20 agentes em 2 lotes (16 + 4), executar em paralelo, depois juntar.

Caso de uso: Scan massivo do SharePoint. Lote 1 (A1–A8, S1–S4) varrem projetos core. Lote 2 (A9–A10, S6–S11) varrem segmentos novos. Depois consolidar findings.

batch1 = await parallel(agents.slice(0,16))
batch2 = await parallel(agents.slice(16,20))

Estratégia de Priorização de Workflows

Regras de Priorização (QPrio)

Nível Trigger Ação
Q0 — CRÍTICO User diz "urge", "crítico", "agora"; prazo <2h; claim reequilíbrio Executa imediatamente. Interrompe background. Sem fila.
Q16 — NORMAL Default. Proposta, análise técnica, modelagem de viabilidade Fila padrão. Max 16 agentes paralelos. Fan-out após conclusão anterior.
Q∞ — BACKGROUND Indexação RAG, scan SharePoint, cache warmup Roda quando há slots livres. Interrompível sem perda. Auto-resume.

Exemplo Prático — Workflow Real de 16 Agentes

Cenário: Proposta técnico-comercial para concessão rodoviária. Entrada: edital PDF + briefing cliente (2 páginas). Saída: 10-slide deck + relatório executivo + análise de concorrentes.

Pipeline de Execução

Etapa 1 — Análise (4 agentes paralelos)

  • A9 — Parse regulatório (DNIT, concessões)
  • A7 — Contexto de mercado (concorrentes OEC, CCR)
  • S1 — Specs técnicas (geometria, pavimentos)
  • A10 — Análise de riscos (financeiro, político)

Wall-clock: ~120s (paralelo)

Etapa 2 — Síntese (6 agentes paralelos)

  • A6 — Modelagem financeira (DCF, fluxo caixa)
  • A4 — Cronograma executivo (fases, marcos)
  • A5 — Orçamento SICRO + auxiliares
  • A1 — Análise contratual (TAC, diferenciais)
  • A2 — Levantamento de quantidades CAD
  • A3 — Review jurídico (clausulado)

Wall-clock: ~180s (paralelo)

Etapa 3 — Entrega (6 agentes serializados + consolidação)

  • A8 — Deck 10 slides (5 subtipos Manta: A–E executivos)
  • F-advisory — Parecer técnico
  • A7 — Proposição comercial (18 seções, capa customizada)
  • A6 → A8 — Financeiro no deck (gráficos DCF)
  • A4 → A8 — Cronograma Gantt (3 fases)
  • A14-apresentacoes — Review final (correções de tom, branding)

Wall-clock: ~120s (serial, mas paralelo dentro de etapa 3)

✓ Total Wall-Clock: ~420 segundos (7 minutos)
16 agentes utilizados em paralelo: A1, A2, A3, A4, A5, A6, A7, A8, A9, A10, S1, F-advisory, A14, + 2 slots livres.

Com execução serial (1 agente de cada vez): ~1.200s (20 minutos) — 3x mais lento.

Manutenção e Evolução

Ciclo de Learning (Diário)

A cada workflow executado, registrar em rag_learning_log:

  • Sucesso: Quais agentes falharam? Qual foi o fallback? Tempo real vs. estimado?
  • Anomalias: Agente X demorou 10x mais que normal. Investigar.
  • Gaps: Usário perguntou algo que nenhum agente respondeu? Criar novo agente ou expandir RAG.

Output: EVOLUTION.md semanal com recomendações de melhoria.

Métricas para Monitorar

  • 📊 Taxa de sucesso de routing (% agentes certos de primeira)
  • 📊 Taxa de fallback (% que usaram agente alternativo)
  • 📊 Latência P50 / P95 por agente
  • 📊 Throughput (workflows/hora)
  • 📊 Utilização média de cores (vs. 16 max)
