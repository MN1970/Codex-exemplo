Manta Maestro — Política de Escalagem Automática

Decisão automática de múltiplos agentes, modelos (Sonnet/Haiku) e padrões de orquestração baseado no volume da tarefa

Princípio Fundamental

Regra de Ouro: "Sempre comece com múltiplos agentes em paralelo. Diminua apenas se necessário."

Manta Maestro não pergunta "use 1 agente?" e depois expande. Ao invés disso, ele estima o volume da tarefa, assume fan-out paralelo por padrão, e escolhe Sonnet/Haiku para velocidade e custo.

Resultado: respostas 3–10x mais rápidas que abordagem serial, a um custo controlado.

Classificação de Volume de Tarefa

📊 Banda 1: PEQUEÑO (0–500 tokens input)

Exemplos: "Qual é a SELIC hoje?", "Parse rápido de edital", "Pergunta técnica simples"

Decisão Maestro:

  • 1 agente (Claude ai direto, não precisa paralelismo)
  • Modelo: Haiku (rápido, barato)
  • Padrão: conversa direta
  • Wall-clock: <30s

📊 Banda 2: MÉDIO (500–2000 tokens input)

Exemplos: "Analise este edital de 5 páginas", "Crie um parecer técnico", "Estude este contrato"

Decisão Maestro:

  • 2–4 agentes em paralelo (análise multidimensional)
  • Modelo: Sonnet (balanceado, rápido)
  • Padrão: parallel() votação ou pipeline() 2 etapas
  • Wall-clock: 2–5 min

📊 Banda 3: GRANDE (2000–5000 tokens input)

Exemplos: "Proposta comercial completa", "Análise de viabilidade EVTEA", "Due diligence contratual"

Decisão Maestro:

  • 6–12 agentes em paralelo (fan-out múltiplos aspectos)
  • Modelo: Sonnet primário + Haiku para tasks menores
  • Padrão: pipeline() 3+ etapas, barrier entre fases críticas
  • Wall-clock: 10–30 min

📊 Banda 4: EXTRA-GRANDE (5000+ tokens input)

Exemplos: "Scan massivo de 100 projetos", "Análise forense cronograma", "Reavaliação de toda proposta"

Decisão Maestro:

  • 12–16 agentes em paralelo (máximo fan-out)
  • Modelo: Sonnet análise crítica + Haiku paralelo massivo
  • Padrão: pipeline() com lotes de 16, consolidação em etapa final
  • Wall-clock: 30 min–2 h

Algoritmo de Decisão Automática (Pseudocódigo)

FUNCTION maestro_autoscale(user_input, project_context): # PASSO 1: Estimar volume input_tokens = count_tokens(user_input) context_tokens = count_tokens(project_context) total_tokens = input_tokens + context_tokens # PASSO 2: Classificar volume IF total_tokens < 500: volume_band = PEQUENO num_agents_target = 1 ELSE IF total_tokens < 2000: volume_band = MÉDIO num_agents_target = 3 ELSE IF total_tokens < 5000: volume_band = GRANDE num_agents_target = 8 ELSE: volume_band = EXTRA_GRANDE num_agents_target = 16 # PASSO 3: Detectar complexidade keywords_crítica = ["claim", "reequilíbrio", "litígio", "ANEEL", "ARTESP"] keywords_multi = ["proposta", "viabilidade", "edital", "concessão"] complexidade = BAIXA IF contains_any(user_input, keywords_crítica): complexidade = CRÍTICA ELSE IF contains_any(user_input, keywords_multi): complexidade = MÉDIA # PASSO 4: Selecionar modelo IF complexidade == CRÍTICA: primary_model = OPUS secondary_model = SONNET ELSE IF volume_band == PEQUENO: primary_model = HAIKU secondary_model = NULL ELSE IF volume_band == MÉDIO: primary_model = SONNET secondary_model = HAIKU (se num_agents > 2) ELSE: primary_model = SONNET secondary_model = HAIKU # sempre Haiku paralelo em grande volume # PASSO 5: Escolher padrão de orquestração IF num_agents_target == 1: pattern = DIRECT_CHAT ELSE IF complexidade == CRÍTICA: pattern = PARALLEL_VOTAÇÃO # múltiplas perspectivas, síntese ELSE IF volume_band == MÉDIO: pattern = PIPELINE_2_ETAPAS ELSE: pattern = PIPELINE_3_ETAPAS # análise → síntese → entrega # PASSO 6: Definir SLA (wall-clock estimado) IF pattern == DIRECT_CHAT: sla_minutes = 0.5 ELSE IF pattern == PARALLEL_VOTAÇÃO: sla_minutes = 5 + (num_agents_target / 4) ELSE IF pattern == PIPELINE_2_ETAPAS: sla_minutes = 10 ELSE: sla_minutes = 20 # PASSO 7: Retornar plano de execução RETURN { volume_band: volume_band, num_agents: min(num_agents_target, 16), primary_model: primary_model, secondary_model: secondary_model, pattern: pattern, sla_minutes: sla_minutes, agents_to_dispatch: select_agents(volume_band, complexity), } END FUNCTION

Seleção Automática de Agentes

Baseado em volume + contexto, Maestro seleciona quais dos 20 agentes disparar:

📋 Regra 1: Volume PEQUENO → 1 Agente

Roteamento determinístico por keywords. Exemplo: "edital DNIT" → S1-rodovias. Nenhum parallelismo necessário.

📋 Regra 2: Volume MÉDIO → 3 Agentes (análise tridimensional)

Identifique 3 dimensões da tarefa (técnica, comercial, legal) e dispare 1 agente por dimensão em paralelo.

Exemplo — Edital de concessão rodoviária:

  • S1 (técnico) — análise geométrica e pavimentos
  • A7 (mercado) — contexto competitivo e viabilidade
  • A9 (regulatório) — conformidade DNIT/ARTESP

Wall-clock: 3 análises em paralelo = 1 hora. Serial: 3 horas.

📋 Regra 3: Volume GRANDE → 8 Agentes (proposta completa)

Dispare todos os agentes horizontais relevantes em 2–3 etapas:

Etapa 1 (paralelo): Análise (A9 regulatório, S1 técnico, A7 mercado, A10 risco) — 4 agentes

Etapa 2 (paralelo): Síntese (A6 modelagem, A5 orçamento, A4 cronograma, A3 legal) — 4 agentes

Etapa 3 (serial): Entrega (A8 deck, A1 review final) — conforme síntese da etapa 2

Wall-clock: ~25 min (paralelo). Serial: ~8 horas.

📋 Regra 4: Volume EXTRA-GRANDE → 16 Agentes (máximo fan-out)

Dispare todos os 20 agentes em lotes de 16 (2 lotes sequenciais) ou use pipeline() com N items em paralelo.

Caso: Scan de 100 projetos no SharePoint

Lote 1 (16 agentes × 50 projetos em paralelo) → Lote 2 (20 agentes × 50 restantes) → Consolidação

Wall-clock: 2 × 30 min + 10 min consolidação = 70 min. Serial: 1000 horas.

Exemplos de Decisão Automática

Exemplo 1: "Qual a SELIC hoje?"

Input tokens: 15 (pequeno)
Volume band: PEQUENO
Complexidade: Baixa (pergunta factual)
Decisão Maestro: Haiku, 1 agente, conversa direta, wall-clock <30s
Ação: Responder direto em Claude AI. Não dispara workflow paralelo.

Exemplo 2: "Analise este edital de concessão rodoviária de 10 páginas e me dê um parecer"

Input tokens: 1200 (médio)
Volume band: MÉDIO
Complexidade: Média (análise multidimensional)
Decisão Maestro: 3 agentes paralelos: Sonnet + Sonnet + Haiku, pipeline 2 etapas, wall-clock 5–10 min
Agentes: A9 (regulatório) + S1 (técnico) + A7 (mercado)
Ação: Dispara pipeline(): análise paralela (A9, S1, A7) → síntese (A8 parecer) → entrega

Exemplo 3: "Preciso de uma proposta comercial completa para essa concessão até amanhã"

Input tokens: 3500 (grande)
Volume band: GRANDE
Complexidade: Alta (multi-disciplinar)
Decisão Maestro: 8 agentes paralelos: 4 Sonnet + 4 Haiku, pipeline 3 etapas, wall-clock 25 min
Agentes: Etapa 1: A9, S1, A7, A10 | Etapa 2: A6, A5, A4, A3 | Etapa 3: A8, A1
Ação: Dispara Workflow: fan-out 8 agentes em 3 etapas, consolidação em final, entrega 25 min

Regras Invioláveis da Autoscaling

Regra 1: Sempre comece com múltiplos agentes

Padrão é fan-out paralelo. Diminua apenas se volume < 500 tokens. Nunca assuma serial por padrão.

Regra 2: Haiku é padrão para paralelo massivo

Em volume grande/extra-grande, use Haiku para tasks suporte/paralelo em massa. Sonnet para análise crítica.

Regra 3: Sonnet é padrão para análise única

Se volume médio e apenas 1 agente necessário, use Sonnet (não Haiku). Qualidade > velocidade em análise crítica.

Regra 4: Opus apenas para reequilíbrio/M&A

Opus é raro. Use apenas em claims de reequilíbrio, due diligence, decisões que movem múltiplos milhões. Padrão: Opus + votação Sonnet.

Regra 5: Pipeline sem barrier é padrão

Não use parallel() com barrier desnecessário. pipeline() sem barrier deixa wall-clock baixo.

Monitoramento e Ajuste Contínuo

A cada execução, Maestro registra em rag_learning_log:

Métrica O que monitorar Ação se desviar
Wall-clock real Tempo real de execução vs. SLA estimado Se real > SLA × 1.5, revisar seleção de agentes ou modelo
Taxa de sucesso % de agentes que completam sem erro Se <90%, investigar fallback (qual agente falhou?)
Custo total Input + output tokens × preço modelo Se > orçamento esperado, diminuir num_agents ou trocar para Haiku
Qualidade da resposta Score de satisfação do usuário (1–5) Se <3, reviewar seleção de agentes (talvez Sonnet necessário, não Haiku)
🔄 Ciclo de Ajuste (Semanal)

Toda segunda-feira (ou conforme carga), Maestro analisa rag_learning_log da semana anterior:

  • Quais combinações volume/modelo/agentes tiveram melhor wall-clock?
  • Quais tiveram pior taxa de sucesso?
  • Qual foi o custo médio por tipo de tarefa?
  • Atualizar maestro_autoscale_policy.md se regras mudam
